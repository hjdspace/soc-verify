Problem: ToolCard.tsx is a 1,653-line monolith — every tool's summary logic, body renderer, diff-stats computation, and shared UI primitive lives in one file. Adding or modifying a single tool body forces reading the entire file. The switch statements in buildSummary() and ToolBody are duplicated dispatch tables that must stay in sync.

Solution: Extract each category of tool bodies into its own module under chat/tool-bodies/. ToolCard keeps only the header, expand state, and a single dispatch table that maps tool name to body component + summary builder.

  • ▸ Locality: adding a new tool body touches one file, not 1,653 lines
  • ▸ Leverage: ToolCard's interface stays { message } — callers unchanged
  • ▸ Tests: each body module tested through its own props, not via ToolCard orchestration
  • ▸ AI-navigability: searching for "SimRunBody" lands in an 80-line file, not a 1,653-line file
  • ▸ Deletion test: deleting ToolCard concentrates complexity into RightPanel — it earns its keep as the dispatch shell

flowchart TD

Problem: buildSummary() and ToolBody are two switch statements over the same tool-name keys. Adding a new tool means editing both — and if you forget one, the card silently shows the wrong summary or falls back to GenericBody. The duplication is a seam with no leverage.

Solution: Replace both switches with a single TOOL_REGISTRY map: { [toolName]: { summary, Body } }. ToolCard does one lookup, gets both summary and body.

  • ▸ Locality: one place to register a tool — bugs can't hide in dispatch mismatch
  • ▸ Deletion test: deleting the registry forces both switches back — it earns its keep
  • ▸ Tests: registry entries are plain data — testable without rendering

Problem: tool-helpers.ts is a grab-bag of 6 unrelated domains. The todo parser (280 lines, including getLatestTodoState) is consumed by TodoPanel.tsx, not by ToolCard — yet it lives in ToolCard's helper file. The diff engine (computeSimpleDiff) is a general algorithm that could serve DiffReviewView too, but is locked inside the chat helpers barrel.

Solution: Split by domain. Each module has a focused interface and can be tested independently. TodoPanel.tsx imports from todo-parser.ts directly.

  • ▸ Locality: todo parsing bugs concentrate in todo-parser.ts, not an 854-line grab-bag
  • ▸ Leverage: diff-engine.ts is reusable beyond ToolCard (e.g. DiffReviewView)
  • ▸ Tests: each parser tested through its own narrow interface
  • ▸ Deletion test: deleting the barrel concentrates imports — each domain earns its own file

Top recommendation

Candidate 1: Split the ToolCard monolith into per-category body modules

ToolCard.tsx at 1,653 lines is the single largest file in the chat module — 3× larger than the next biggest component. It's the hottest file in the commit history (13 commits in recent history, touching everything from subagent tiles to ask-question formatting). Every new tool type forces a change to this one file, and every change risks breaking unrelated tool bodies. Splitting by category gives each tool body its own module with a focused interface, while ToolCard stays as the thin dispatch shell. This is the refactor with the highest locality payoff and the lowest risk of behavioral change.

Candidates 2 (registry unification) and 3 (tool-helpers split) are natural follow-ups once the bodies are extracted — the registry becomes trivial when bodies are already separate modules, and tool-helpers split is independent but lower urgency.
